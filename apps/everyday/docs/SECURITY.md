# Модель безопасности

## Граница доверия

Пользователь браузера аутентифицируется непрозрачной HttpOnly-сессией.
Каждый mesh-узел синхронизации является доверенным участником: доступ к
`MESHKEEPER_SYNC_TOKEN` фактически даёт доступ к синхронизируемым рабочим
данным и хешам паролей для офлайн-входа. Такой токен нельзя выдавать обычному
пользователю или встраивать во frontend/APK.

Если одна база содержит несколько организаций, capability обязательно
ограничивается списком GUID через `MESHKEEPER_SYNC_WORKSPACES`. Такой scope
применяется симметрично к GET/pull, входящему push, offline bundle и CAS chunks:
peer не получает пользователей, чат, бухгалтерию, знания, manifests или файлы
другой организации. Обе стороны постоянного соединения должны использовать
одинаковый scope. Отсутствие переменной сохраняет legacy-режим доверенной ноды
со всеми организациями и допустимо только для физически контролируемого сервера.
CAS endpoint не доверяет одному предъявленному SHA-256: он независимо ищет
ссылку в ТМЦ, custody, wiki либо chat текущего scope. Scoped snapshot включает
chat CAS в manifest, поэтому full-узел догружает свой файл, но тот же bearer
получает `403` для файла другой организации даже при известном хэше.
Android передаёт scope в JNI отдельно от защищённого Keystore-токена. Scope
никогда не добавляется в service Intent или WebView bridge; нативный launcher
нормализует, дедуплицирует и ограничивает список сотней GUID.

Мобильный набор нескольких capability целиком хранится как отдельный AES-GCM
ciphertext с собственным AAD `sync-capabilities/v1`. Он расшифровывается только
foreground service непосредственно перед JNI-вызовом, не восстанавливается в
поле UI и не передаётся через Intent/WebView. Нативная форма до шифрования
проверяет GUID, длину и уникальность токенов, URL и лимиты peers.

Для нескольких независимых mesh-групп используется
`MESHKEEPER_SYNC_CAPABILITIES`: у каждой записи отдельный bearer, scope и peers.
HTTP GET/pull/push и CAS сначала постоянным по времени сравнением выбирают
capability, затем применяют только её scope. Неверный JSON, повтор секрета,
пустой scope и неоднозначное смешивание с legacy upstream приводят к отказу
старта, а не к доступу ко всей базе. UDP discovery пока включается только для
единственной capability; при нескольких используются явно заданные peers.

## Защита backend

- Argon2id для новых паролей; длина нового пароля 12–128 символов.
- Сессионный токен хранится в БД только как SHA-256, cookie — HttpOnly,
  SameSite=Strict и Secure в production.
- Изменяющие browser-запросы требуют same-origin `Origin`.
- Все запросы ограничены 32 МБ; `metadata_json` — 64 КБ.
- CSP, запрет iframe/MIME sniffing, строгая referrer-policy и Permissions-Policy.
- API и sync-ответы получают `Cache-Control: no-store`.
- Не-loopback bind требует secure-cookie; каждый peer синхронизации требует HTTPS.
  Незашифрованный HTTP разрешается только для loopback или явной тестовой
  настройки `MESHKEEPER_ALLOW_INSECURE_SYNC=1`.
- Для автономного вступления QR-приглашения передаются только как SHA-256
  capability-отпечатки. Bearer-токен из QR никогда не попадает в журнал;
  принимающий узел локально проверяет доказательство владения токеном.
  Приём сырого формата старых узлов включается только через
  `MESHKEEPER_SYNC_INVITES=1`, причём перед сохранением токен хешируется.
- Критические операции требуют Ed25519-подпись зарегистрированного устройства
  над методом, путём, временем, nonce и SHA-256 тела. Nonce одноразовый,
  отозванные устройства отклоняются до начала транзакции. Это также обязательно для
  добавления/исключения участника, изменения роли, приглашения,
  настроек организации и её дерева. Отдельная подпись также требуется для
  смены профиля/пароля, отзыва устройства, backup import/export, доверия к
  ключам нод, изменения peers, ручной синхронизации и политики хранения CAS.
  Сама мутация и добавление Ledger V2
  события выполняются в одной SQLite-транзакции.
- Подписанный journal v2 переносит scoped-реестр устройств: неизменяемый
  `deviceId`, GUID владельца, Ed25519 public key и monotonic tombstone отзыва.
  До trust bootstrap каждый входящий device-proof сверяется с этим реестром:
  actor обязан быть владельцем ключа, а время события — попадать между
  регистрацией и отзывом. Старый offline snapshot не снимает отзыв, повторная
  регистрация того же `deviceId` не может заменить ключ или оживить устройство.
- Членство реплицируется как `versioned-tombstones/v1`: GUID организации и
  человека, Lamport-revision, active, права, должность, Ledger hash и
  детерминированный `versionHash`. Исключение не кодируется отсутствием
  строки: tombstone передаётся всем нодам. При равной ревизии revoke всегда
  сильнее role-update; более новая явная операция вступления может создать
  следующую active-ревизию. Неверный hash, дубль ключа или отсутствующее
  Ledger-событие отклоняют весь journal до trust bootstrap и до изменения ACL.
  Для active/revoke дополнительно проверяется совместимый тип события
  (`membership_create/update/remove/join` или `workspace_create`). Все
  административные ветки обязаны нести полный device-proof; только
  capability-вступление может иметь `membership_join` без него, причём actor GUID
  обязан совпадать с GUID вступающего. GUID цели в `fromLabel/toLabel` также
  обязан точно совпадать с пользователем version-record: валидная подпись над
  изменением Алисы не может быть повторно использована для назначения прав Бобу.
- Ledger V2 подписывается ключом узла, связывается `prev_hash` и использует GUID
  организации, пользователя и объекта. Доказательство устройства сохраняется
  внутри события и повторно проверяется при старте и при импорте sync-журнала.
  Невалидный импорт откатывается целиком через SQLite savepoint.
- Создание и изменение master-карточки ТМЦ также требуют Ed25519 device-proof.
  Подписываемые процедуры запрещено смешивать с другими вызовами в tRPC batch:
  действует инвариант «один HTTP-запрос — одна пользовательская транзакция».
  Добавление фотографии двухфазно: `content.ingest` кладёт bytes в локальный
  CAS, после чего `items.addPhoto` принимает только известные `cas:sha256`, GUID
  карточки и созданный клиентом GUID фото. Маленькое signed request body
  сохраняется в Ledger V3; `photo_add` коммитит URL оригинала/thumbnail,
  checksum и title-флаг. Импорт до доверия к ноде повторно вычисляет commitment
  и сравнивает снимок с точным пользовательским intent. Подмена trusted-нодой с
  новой подписью snapshot отклоняется. Ошибка Ledger откатывает строку фото.
  Снимки, созданные старой версией вместе с карточкой, остаются явно legacy:
  система не приписывает им несуществовавшую пользовательскую подпись.
  Документы используют тот же двухфазный путь: `items.addDocument` принимает
  только проверенную локальную CAS-ссылку. Подписанное намерение фиксирует GUID
  карточки и документа, имя, MIME, SHA-256 и ACL. При mesh-import эти поля
  сверяются с Ledger V3 даже после корректной переподписи снимка доверенной
  нодой; документы без `ledgerHash` остаются явно legacy.
  Регрессионный sync-сценарий физически останавливает upstream, создаёт документ
  на оставшейся ноде, затем проверяет восстановление точных CAS-байтов на full-node,
  сохранение ACL, сокрытие от viewer и отказ принять запоздавший snapshot.
  Клиент использует небатчевый transport. Обычная правка создаёт одно событие;
  принятие заявки атомарно создаёт два причинно связанных доказательства:
  commitment решения и производное полное master-состояние.
- Master-состояние реплицируется как `item-state/v1` portable branch. Commitment
  включает item/workspace/actor GUID, parent, depth, время и полный набор
  административных полей. Import до node-trust проверяет device-proof, Ledger
  binding, hash ветви и соответствие materialized snapshot. Конкурирующие
  offline-ветви выбираются по `(depth, versionHash)`. Операционные поля после
  выдачи, возврата, перемещения, инвентаризации или fault-события проверяются их
  специализированными custody/fault-записями и не откатываются старой master-
  версией.
- Комментарий ТМЦ — append-only `ledger-records/v1`: SHA-256 commitment включает
  точный текст, GUID организации/карточки/автора/записи и время. Он связан с
  `item_comment` Ledger V2 и обязательным device-proof. Импорт сначала проверяет
  эту связь и лишь затем доверие к snapshot-ключу; пересчёт snapshot и record
  hash после подмены текста не помогает атакующему.
- Lifecycle неисправности использует `append-only-branches/v1`. Корневой
  `fault_report` и каждый `fault_update` требуют отдельный Ed25519 device-proof;
  запись коммитит parent, глубину, автора, ТМЦ, описание, важность, решение и
  CAS-ссылку. Конкурирующие offline-решения сохраняются обе, materialized state
  выбирается по `(depth, recordHash)`, поэтому порядок доставки не влияет на
  результат. Подмена решения с пересчётом node snapshot отклоняется связью с
  исходным Ledger payload hash.
  Первая операция над legacy-неисправностью создаёт device-signed
  `fault_adopt`; система не приписывает старым данным несуществовавшую подпись.
- Заявки на изменение используют `portable-branches/v1`: request и decision
  подписываются устройством, commitment включает portable patch, снимок полей
  до изменения, автора, item/workspace GUID, parent, решение и причину.
  Локальные ID не пересылаются как идентичность: user связывается по GUID,
  status по slug, именованные справочники по `(workspace, name)`. Параллельные
  accept/reject сохраняются ветками; победитель `(depth, recordHash)` либо
  применяет patch, либо восстанавливает подписанное состояние «до». Legacy-
  заявка вводится в модель явным `change_adopt`. Более поздний прямой
  device-signed `items.update` причинно перекрывает старое решение, поэтому
  повторный sync не откатывает последующую ручную правку.
- Склады, площадки и словари используют `portable-branches/v1`: каждая версия
  коммитит GUID сущности/организации/автора, parent, глубину, активность и
  текстовые поля и связана с device-signed `config_*` Ledger event. Импорт
  проверяет эту связь до bootstrap доверия к mesh-ноде, сохраняет параллельные
  ветви и материализует одинаковую голову по `(depth, versionHash)`.
- Произвольное дерево организации использует отдельную
  `organization-node/v1` летопись. Версия коммитит GUID раздела, родителя,
  организации, автора и ответственного, все отображаемые поля, active tombstone
  и parent hash; соответствующий `organization_node_*` Ledger event обязан
  содержать device-proof. Импорт сверяет производный snapshot, детерминированно
  сливает offline-ветви и запрещает циклы. Повторная подпись подменённого
  snapshot ключом доверенной ноды не заменяет подпись пользователя.
- Сессии инвентаризации используют `append-only-records/v1`. `create` коммитит
  номер и исходный список `(itemGuid, expectedQty)`, каждый `check` — GUID ТМЦ,
  фактическое количество и признак проверки, `complete` — итоговые счётчики.
  Все три типа связаны с отдельным Ed25519 device-proof; delta может ссылаться
  на уже сохранённый корень. Импорт проверяет hash, Ledger evidence и пределы
  размеров до доверия к ключу ноды, затем заново материализует session/results.
  Inventory Ledger V3 дополнительно переносит исходное безопасное JSON-тело
  HTTP-запроса. Оно является частью node-chain, его SHA-256 уже входит в
  Ed25519 device signature. Remote verifier пересчитывает hash, проверяет
  endpoint и сравнивает фактическое количество/checked с подписанным input.
  Тест отдельно создаёт новый валидно node-signed event с повторно приложенным
  device-proof, но `actualQty=99` вместо подписанного `7`; импорт его отклоняет
  как semantic substitution.
- Завершённая сверка экспортируется как `everyday-inventory-act` v1. Поле
  `canonical` содержит base64 точных JSON-байтов (количества представлены
  каноническими десятичными строками), `hash` — их SHA-256. Нода подписывает
  transcript `everyday/inventory-act/v1\n{hash}` ключом Ed25519 и прикладывает
  public key. Проверяющий обязан декодировать `canonical`, сопоставить его с
  `act`, пересчитать hash и лишь затем проверить подпись; перечисленные в акте
  Ledger/record hashes связывают его с пользовательскими device-proof.
  `inventory.verifyAct` выполняет эти проверки на принимающей ноде, сравнивает
  ключ по декодированным Ed25519 bytes с local/approved node trust store и лишь
  после этого ищет организацию в memberships вызывающего пользователя. Затем
  независимо строит акт из локального materialized state и сообщает отдельные
  состояния `verified`, `untrusted_key`, `foreign_organization`,
  `history_missing`, `history_mismatch` или `invalid`. Так отсутствие mesh-delta
  не маскируется под криптографическую подделку и не пробивает изоляцию tenant.
  `createdAt/completedAt` берутся из переносимых create/complete records, а не
  из времени локальной материализации, поэтому акт побайтово воспроизводится
  другой нодой после partition/heal.
  Offline CLI `--verify-inventory-act` вызывает тот же bounded verifier без
  открытия SQLite и возвращает машинно-читаемый JSON и exit code `0/2`. Это
  независимая проверка целостности файла и Ed25519 node-proof, но не утверждение
  доверия к ключу: trust store, membership и локальная история доступны только
  полному `inventory.verifyAct` внутри организации.
- «Удаление» ТМЦ реализовано как delete-wins `itemTombstoneMode=monotonic/v1`.
  Tombstone коммитит GUID организации, карточки и автора, Ledger hash и время;
  связанное `item_archive` обязано иметь полный device-proof. Проверка проходит
  до trust bootstrap и повторяется локальным integrity audit. Карточка, история,
  фото/CAS-ссылки физически не стираются, а старый активный snapshot не снимает
  `archived`. Выданную или ожидающую передачи карточку архивировать нельзя.
- Весь sync-snapshot (история и текущее производное состояние) имеет общий
  SHA-256 и Ed25519-подпись узла. Подмена карточки, прав, списка участников,
  сообщения либо ledger-события в пути обнаруживается до начала импорта.
  Journal v2 также несёт монотонный подписанный `journalSequence` и
  `journalScope`. Узел атомарно хранит последнюю квитанцию для каждого
  ключа ноды и scope: точный повтор идемпотентен, меньший номер
  отклоняется как rollback, а два разных hash с одним номером — как
  эквивокация. Квитанция пишется в том же SQLite savepoint только
  после проверки всех ledger/chat/accounting/wiki связей. Legacy journal v1
  не имеет anti-rollback proof и поэтому не импортируется.
- Конкурирующие офлайн-выдачи разным сотрудникам не разрешаются правилом
  «последний победил». Предмет освобождается и переводится в `needs-check`, а
  `conflict_detected` добавляется в подписанную историю и разносит карантинное
  состояние остальным устройствам до решения уполномоченным сотрудником.
  Список конфликтов фильтруется по выбранной организации. При закрытии
  организация определяется сервером по ID конфликта до проверки прав, поэтому
  участник другой организации не может ни увидеть, ни закрыть такую запись.
- Выдача и возврат создают append-only custody-проводку
  `everyday/custody-entry/v1`, связанную с точным Ledger hash. В commitment
  входят GUID организации, предмета и работника, знак/количество, срок,
  metadata и время. Importer до trust bootstrap проверяет hash, тип
  `transfer_receive/send`, actor/item/workspace, количество и обязательный
  device-proof. Для количественных материалов свежая нода восстанавливает
  активные партии и ответственных из этих проводок; подмена `4` единиц на `2`
  отклоняется даже после пересчёта snapshot и custody hash доверенной нодой.
  Фото выдачи переводится из data URL в CAS и не раздувает текстовый journal.
  Фото списания проходит отдельную двухфазную схему `writeoff-photo`: загрузка
  требует права списания и выдаёт одноразовый часовой grant, привязанный к
  user/workspace/item/operation/hash. `history.writeOff` атомарно погашает его
  и записывает Ledger V3 commitment количества, комментария и CAS-ссылки.
  Переносимый журнал содержит только компактное подписанное намерение; import
  отклоняет замену фото, предмета, организации, UUID или количества. Действуют
  persisted лимиты 10 загрузок и 64 МиБ в минуту на участника.
  Загрузка документа из карточки разделена на два права: scoped CAS ingest с
  `purpose=item-document` требует `itemId`, совпадения организации и
  `manageDocuments`, затем `items.addDocument` повторно проверяет те же
  привязки, CAS MIME/hash и создаёт Ledger V3 intent. Поэтому роль управления
  документами без `createItems` работает, но не получает общий канал загрузки
  произвольных blobs. UI ограничивает исходный файл 20 МБ: после base64 и JSON
  запрос остаётся внутри общего лимита 32 МБ. Интернодовый chunk-протокол и CAS
  принимают до 32 МБ. Интерфейс явно выбирает ACL `members/accounting/managers`.
  Выдача дополнительно требует tenant-bound QR V2: сервер проверяет Ed25519
  node-proof, доверие к ключу, GUID организации и точное соответствие карточке.
  Legacy-код годится только для поиска и инвентаризации. Каждая штучная единица
  требует отдельного скана; массовый API принимает отдельное доказательство на
  каждый item. QR входит в точное тело device-signed Ledger V3, однако API
  истории отдаёт лишь `{itemId, version, sha256}`, чтобы не распространять
  копируемую бирку и остальные поля запроса. Выдача новой бирки защищена правом
  `editItems`. Это не доказывает аппаратное происхождение снимка и не обнаруживает
  физический клон настоящей наклейки.
- Bit-проводки проверяются до trust bootstrap: две строки должны восстановить
  `txHash`, а подписанное пользовательским устройством Ledger-событие — совпасть
  по организации, actor, типу, сумме и счёту отправителя. Поэтому нода не может
  подменить получателя или сумму и легализовать это новой подписью snapshot.
  `bit.recipients` ограничен активной организацией и возвращает только
  GUID/имя/должность без телефона. `bit.myTransactions` выбирает проводки через
  счета текущего пользователя; вся летопись требует `viewAccounting`, эмиссия —
  `manageAccounting`, остальные операции — `useBit`. Эти права повторно
  проверяются backend независимо от видимости пункта меню.
  Для `bit.sale` продавец обязан быть активным участником той же организации и
  текущим `responsibleUserId` связанного ТМЦ. Проверка выполняется внутри одной
  SQLite-транзакции до `accounting::post`; поэтому подмена продавца не создаёт
  ни транзакцию, ни строки debit/credit, ни Ledger event. UI показывает только
  ТМЦ, числящиеся за выбранным продавцом, но это лишь удобство, не security gate.
  Двухфазная продажа повторно использует signed custody transfer: предложение
  подписывает ответственный продавец, принятие — только указанный покупатель.
  Цена хранится как положительное целое число; при accept backend ещё раз
  проверяет ответственность продавца и права обеих сторон, затем в одной
  транзакции создаёт сбалансированную Bit-проводку, `transfer_receive`,
  `bit_sale`, custody-записи и меняет ответственного. Недостаток средств,
  устаревший владелец и replay оставляют предложение pending и не создают
  полупроводок. Предложение экспортируется как `device-signed-intent/v1` со
  стабильными GUID организации, ТМЦ, продавца, покупателя и предложения —
  локальные числовые ID не считаются переносимым доказательством. Importer
  сверяет цену и комментарий с сохранённым телом V3-запроса продавца. Для
  `accepted/rejected` он требует отдельное событие устройства покупателя, а для
  `accepted` — ещё и совпадающую portable Bit-проводку. Монотонное слияние не
  позволяет pending/rejected затереть accepted. Подмена цены даже после
  пересчёта record hash и подписи snapshot доверенной нодой отклоняется.
  Для количественной позиции предложение разрешено только из активного holding
  продавца. Подписывается точное положительное количество; перед Bit-проводкой
  остаток проверяется повторно внутри той же транзакции. Accept переносит только
  указанную часть партии, сохраняя остаток продавцу. Importer нормализует JSON
  `4`/`4.0` как одно точное `f64`, но отклоняет строку, NaN, бесконечность,
  неположительное или изменённое значение.
  Прямая передача двухфазна: `prepare` сохраняет Ledger hash подписанного
  намерения отправителя и источник количества (склад либо уже выданная партия),
  `accept` подписывается получателем. Только после accept появляются debit
  отправителя и credit получателя; reject не двигает custody. Передача выданных
  материалов не списывает склад второй раз. Подмена GUID получателя при
  пересчёте custody/snapshot hash не проходит связь с actor/toLabel Ledger.
- Сообщение чата связано с отдельным событием `chat_message`: проверяются GUID,
  организация, автор и точный текст. Подмена строки в SQLite обнаруживается при
  старте; неверное сообщение из peer откатывает весь импорт. Отправка требует
  device-proof, ограничена 20 сообщениями в минуту на пару организация/участник
  и подавляет быстрый дубль. Проверка и вставка находятся в одной SQLite-
  транзакции: запрос №21, дубль и текст длиннее 4000 символов не оставляют ни
  строки сообщения, ни Ledger-полусобытия. Счётчик выводится из сохранённых
  сообщений, поэтому убийство и restart процесса его не сбрасывают. Лимит одного
  участника не блокирует остальных; это отдельно проверяется Rust-тестом.
  CAS ingest для чат-файлов не использует право `createItems`: он требует
  `purpose=chat-attachment`, UUID будущего сообщения и членство. В SQLite
  сохраняется одноразовый grant `(workspace,user,message,hash)`, действующий час;
  `chat.send` проверяет точный CAS MIME/hash и атомарно помечает grant
  использованным вместе с Ledger/сообщением. Чужой UUID, повторный hash, ложный
  MIME и replay отклоняются. До записи blob действуют persisted лимиты 10
  файлов/мин и 1000/сутки; после определения размера транзакция откатывает CAS
  при превышении 64 МБ/мин, 512 МБ/сутки на участника или 2 ГБ/сутки на
  организацию. Поэтому неудачная/заблокированная отправка не превращает CAS в
  обход антиспама.
- URL peer проверяется: запрещены credentials, path, query и fragment. HTTP
  разрешён только для loopback либо явной изолированной тестовой LAN.
- UDP discovery аутентифицирует точную схему HMAC-SHA256 общим mesh-токеном,
  ограничивает размер 2048 байтами и время ±120 сек, кэширует nonce от replay,
  отклоняет self-анонсы,
  DNS и публичные IP. Обнаружение добавляет только маршрут: trust Ed25519-ключа
  ноды по-прежнему подтверждается отдельно.
- Число прямых peers ограничено 32, собственный адрес добавить нельзя. Для
  больших сетей используется разреженная топология с резервными связями, а не
  полносвязная схема с квадратичным числом обменов.
- Административный `sync.audit` повторно проверяет SQLite, все ledger-подписи,
  связи чата, обязательные GUID и подписанный snapshot, а также публикует головы
  account-chain и счётчики. Успешный локальный аудит доказывает целостность
  полученной копии; равенство с конкретной удалённой нодой требует сравнения
  heads/fingerprint после успешного обмена.
- Вложения не встраиваются в sync-snapshot: подписывается CAS-ссылка и manifest,
  данные скачиваются авторизованными chunks по 64 КиБ. Частичная загрузка
  сохраняется в SQLite и не становится доступной приложению, пока SHA-256 всего
  объекта не совпадёт с адресом. Аудит считается нездоровым при отсутствующем
  либо незавершённом blob. Браузерные формы ТМЦ и wiki используют двухфазный
  `content.ingest`: подписанная предметная транзакция содержит `cas:sha256`, а
  не base64 файла.
- Wiki-вложения принимаются только с правом `editKnowledge`: отдельный ingest
  выдаёт на один час одноразовый grant для точных user/workspace/revision/hash.
  На пользователя действуют лимиты 20 файлов и 128 МиБ в минуту, 1000 файлов и
  512 МиБ в сутки; браузер дополнительно ограничивает один файл 20 МБ. Сохранение
  ревизии проверяет каталог CAS, фактический MIME и погашает весь набор grants в
  одной транзакции, поэтому ошибка не создаёт частично авторизованную страницу.
- Новые wiki-ревизии используют клиентские `workspaceGuid`, `pageGuid` и
  `revisionGuid`. Ledger V3 сохраняет компактное signed request body, а import
  до доверия к ноде сравнивает с ним slug, заголовок, текст, ACL, parent и все
  CAS-вложения. Старые ревизии остаются явно legacy и не получают ложной
  атрибуции пользовательского intent.
- Новые сообщения чата используют клиентский `messageGuid` и V3 commitment для
  workspace/author GUID, текста и полного списка CAS-вложений. Import сверяет
  commitment с точным Ed25519-signed request body до node trust; подмена текста,
  MIME, имени или CAS-хэша доверенной нодой отклоняется. Файлы сообщения
  загружаются отдельно и восстанавливаются только content/full-нодами.
- Файловый transport bundle v2 не раскрывает journal посреднику: используется
  XChaCha20-Poly1305 с новым 192-битным nonce, фиксированным AAD и ключом
  HKDF-SHA256, доменно отделённым от bearer/CAS. Wrong-key и tampering
  отклоняются AEAD до разбора journal; затем отдельно проверяется Ed25519.
- `meshkeeper-frame` является безключевым transport bridge: stdin payload
  ограничен 32 МБ, число/общий base64url-объём кадров ограничены, каждый MKST
  chunk проверяется до удержания, а итог — полным SHA-256. CLI не открывает БД,
  не расшифровывает bundle и не может авторизовать импорт. Поэтому serial/LoRa/
  USB-драйвер допустимо считать недоверенным переносчиком; изменение, смешение
  transfer ID, конфликтующий retry и неполная доставка завершаются fail-closed.
- Между независимыми организациями передаётся не scoped journal, а отдельный
  opaque envelope. Полезная нагрузка шифруется XChaCha20-Poly1305 на одноразовом
  X25519 shared secret; HKDF-SHA256 привязывает ключ к адресу получателя, а
  Ed25519 подписывает заголовок и ciphertext. Relay проверяет подпись, TTL,
  размер, replay и proof-of-work, хранит не более 4096 живых конвертов и не
  видит GUID организаций, вид транзакции или текст. Получатель дополнительно
  сверяет свой workspace и ключ отправителя с локальным доверенным каталогом.
  `POST /mesh/envelopes`, адресный `GET /mesh/envelopes/{destination}` и
  ограниченный 128 элементами `GET /mesh/gossip` доступны на sync-only
  listener; тот же ciphertext имеет отдельный MTU payload kind и может идти
  через IP, BLE, Wi-Fi Direct, LoRa или ручной store-and-forward.
  Фоновый IP-gossip включается отдельным `MESHKEEPER_RELAY_PEERS`; эти связи не
  получают capability какой-либо организации и переносят только конверты.
  Адрес gateway создаётся подписанной операцией `interorg.ensureIdentity`, а
  X25519 secret в БД обёрнут AEAD-ключом, производным от node signing identity.
  Контрагент добавляется только администратором через подписанный
  `interorg.trustContact`; QR/визитка должна содержать одновременно GUID,
  X25519 public key и Ed25519 signing key и подтверждаться по независимому
  каналу. `interorg.send` ставит envelope в offline-очередь, `interorg.inbox`
  показывает только расшифрованные сообщения доверенных контрагентов,
  `interorg.accept` идемпотентно создаёт отдельный Ledger-факт принятия и в той
  же SQLite-транзакции ставит в обратную store-and-forward очередь зашифрованную
  `receipt.accepted`. Она переносит исходный `transactionId` и полный V3 Ledger
  event: точное сохранённое тело `interorg.accept`, device public key/signature,
  node public key/signature, `prevHash` и event hash. Отправитель заново строит
  canonical bytes, проверяет обе Ed25519-подписи и body hash, затем меняет scoped
  outbox из `queued` в `accepted` только если node key совпал с тем же доверенным
  контактом, workspace GUID, event type, исходные envelope/transaction ID и
  подписанное тело запроса совпадают, а первая квитанция ещё не принята.
  Разные padded/unpadded Base64-представления ключа сравниваются по декодированным
  32 байтам. Квитанция без V3 proof или для чужого/выдуманного transaction ID
  карантинится и ничего не подтверждает. Контрагент видит псевдонимные actor/device
  GUID и публичные ключи из proof, но не получает профиль, склад или журнал.
  Для новых inbox-записей сохраняется точная копия исходного opaque envelope,
  независимая от короткого relay TTL. `sync.audit` повторно проверяет его
  Ed25519-подпись и исходные границы TTL, открывает XChaCha20-Poly1305 и сверяет
  sender/recipient/kind/transaction/body с локальной строкой; для принятой
  записи дополнительно требуется ровно один V3 Ledger-факт с подписанным
  `envelopeId`. Старые строки без source envelope считаются явно legacy.
  Аудит также перестраивает все сохранённые accepted receipt proof; локальная
  SQL-подмена делает узел `healthy=false`, а панель показывает точную ошибку.
  Новый envelope
  с уже виденным `transactionId` того же контрагента помещается в
  карантин: транспортный UUID не может обойти семантическую идемпотентность или
  подменить первое принятое тело транзакции.
  Компрометированный контрагент отключается подписанным
  `interorg.revokeContact`: запись каталога сохраняется для аудита, но новые
  send/receive для её ключей прекращаются. Повторное доверие требует новой
  административной подписи и может одновременно заменить оба публичных ключа.
- Android Share receiver принимает только `content://`, потоково применяет лимит
  30 МБ и передаёт ciphertext в авторизованный frontend. Он не обладает API для
  прямой мутации SQLite; импорт сохраняет ACL и обязательный device proof.
- Operational diagnostics хранится только локально, ограничена 500 событиями,
  удаляет control characters и обрезает message/context до 500/2000 символов.
  Повторы дедуплицируются. В контекст peer попадает URL без bearer-токена;
  очистка истории доступна владельцу и требует Ed25519 device proof.
- Самостоятельный выход из организации и удаление аккаунта требуют Ed25519
  device-proof. Выход запрещён, пока за человеком числится оборудование, а
  последний администратор сначала обязан передать полномочия. Для каждой
  организации создаётся `membership_remove` и синхронизируемый tombstone.
  Удаление дополнительно проверяет пароль, отзывает сессии и устройства и
  стирает персональные поля, но сохраняет обезличенный GUID и Ledger-историю.

## Production checklist

1. TLS завершается на nginx/Caddy, backend слушает `127.0.0.1`.
2. `MESHKEEPER_COOKIE_SECURE=1`, sync-токен сгенерирован CSPRNG (32+ байта).
3. Реальные `.env`, БД, бэкапы и FaceKit-импорт не находятся в Git.
4. Локальные диски зашифрованы; для переносимого узла используется сборка
   SQLCipher и отдельный `MESHKEEPER_DB_KEY`.
5. Запускаются `npm run verify`, резервное копирование и проверка восстановления.

Если `MESHKEEPER_DB_KEY` задан обычному бинарнику без feature `encrypted-db`,
узел прекращает запуск. Это fail-closed защита от ошибочного развёртывания
plaintext SQLite вместо ожидаемой SQLCipher-базы.
Server backup также fail-closed: отсутствие пароля, OpenSSL или `sqlite3`
прерывает задачу. Опубликованный архив всегда зашифрован, а restore сначала
проверяет пароль, gzip и `PRAGMA integrity_check`, не перезаписывая рабочую БД.

Android-приложение хранит общий mesh-токен как AES-256-GCM ciphertext. Неэкспортируемый
ключ создаётся в `AndroidKeyStore` (аппаратная защита используется устройством, если
доступна), ciphertext привязан AAD к приложению и назначению ключа. Старое plaintext-
значение из SharedPreferences мигрируется один раз и удаляется; token не передаётся
foreground service через Intent. Backup приложения отключён в manifest.
Ed25519 seed, которым Rust-нода подписывает журнал, защищён тем же механизмом,
но с отдельным AAD purpose. При обновлении Rust сначала читает прежний seed из
SQLite, Java подтверждённо сохраняет ciphertext, а при запуске Rust сравнивает
оба значения и только после точного совпадения удаляет plaintext. Несовпадение
останавливает ноду и сохраняет старую копию для восстановления идентичности.

## Не обещается

Защитные меры снижают риск, но не делают систему «абсолютно безопасной».
Перед хранением паспортных, биометрических или иных особо чувствительных
данных необходимы отдельная модель угроз, аудит и требования применимого
законодательства.
